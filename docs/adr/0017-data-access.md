# 0017. Data access: psycopg 3 with explicit SQL, migrations with Alembic

- Status: accepted
- Date: 2026-09-28

## Context

Synapse's most important queries are PostgreSQL-specific: hybrid retrieval with CTEs, pgvector and BM25 operators, row-level security, advisory locks, `set_config` per transaction ([0003](0003-single-postgres-store.md), [0005](0005-tenancy.md), [0008](0008-audit-log.md)). Security properties live in the database (RLS policies, grants, forced RLS), so they must be written and reviewed as SQL. The job queue ([0004](0004-job-queue.md)) already uses psycopg 3.

## Decision

**Queries**

- psycopg 3 (async) with `psycopg_pool` connection pools. No ORM.
- SQL is written explicitly in each package's repository module, with parameters (never string formatting). Rows map to frozen dataclasses through psycopg row factories.
- All database access goes through `synapse.kernel.database`, which exposes:
  - `Database.tenant_transaction(tenant_id)`: opens a transaction and sets `app.tenant_id` with `set_config(..., true)` before any statement. This is the only way business code gets a connection.
  - `Database.system_transaction()`: no tenant; row-level security then returns nothing from tenant tables. Used only for cluster-wide maintenance, and never from request handlers.
- One pool per process role, connecting as that role's own database user ([0013](0013-secrets-and-network-security.md)).

**Schema and roles**

- All objects live in the `synapse` schema, owned by `synapse_migrator`.
- Runtime login roles (`synapse_api`, `synapse_worker`, `synapse_scheduler`) are members of the group role `synapse_runtime`, which receives table privileges. They own nothing and have `NOBYPASSRLS`. Accounts, sessions, second factors, groups and grants, conversations, the tenant and its settings are `synapse_api`'s alone (migration 0027): the worker and the scheduler hold nothing on them. `tests/db/test_schema_invariants.py` lists every table as the API's alone or shared, and fails on one in neither.
- Cluster-level setup (database, roles, schema, default privileges) is a separate **bootstrap** step that needs a superuser once. It is idempotent: it creates what is missing and resets passwords from the secret files.
- `app_current_tenant()` returns the transaction's tenant or `NULL`. Every tenant-owned table has `tenant_id uuid NOT NULL`, RLS enabled and forced, and one policy `USING (tenant_id = app_current_tenant()) WITH CHECK (tenant_id = app_current_tenant())`, created by one migration helper so that no table gets a hand-written variant.

**Migrations**

- Alembic orders and versions migrations. Migrations are written as SQL (`op.execute`), not autogenerated, and run as `synapse_migrator`.
- A test inspects the live schema after migrating: every table except an explicit list has a `tenant_id` column with RLS enabled, forced and the standard policy; runtime roles own no objects and cannot bypass RLS.

**Tests**

- Database tests run against a real PostgreSQL built from `deploy/postgres/Dockerfile`, in a fresh database per test session. If no test database is configured, those tests **fail** with setup instructions; they are never skipped silently.

## Consequences

- Every query is visible and reviewable; the retrieval SQL can use every PostgreSQL feature directly.
- More hand-written mapping code than with an ORM; kept small by row factories and dataclasses.
- Alembic brings SQLAlchemy as a dependency of the migration tool only; application code does not import it.

## Alternatives considered

- **SQLAlchemy ORM:** its abstractions help least exactly where Synapse is most specific (RLS, vector and BM25 operators, advisory locks), and hide the SQL that security reviews need to see.
- **SQLAlchemy Core:** a reasonable middle ground, but adds a second query layer beside psycopg (which Procrastinate uses anyway).
- **A home-made migration runner with ordered SQL files:** simple, but versioning, branching per optional module ([0012](0012-installer-modules-licensing.md)) and downgrade bookkeeping would be ours to maintain.
