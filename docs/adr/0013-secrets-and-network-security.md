# 0013. Secrets, credentials and network security

- Status: accepted
- Date: 2026-09-28

## Context

Frequent causes of breaches in self-hosted products: secrets or private keys committed to git history, one internal key shared by many services, the same secret given to every container, weak default passwords used when a variable is unset, and unencrypted database connections.

Research: [04-architecture.md, section 7](../research/04-architecture.md).

## Decision

**Secrets**

- Every secret is generated by `synapsectl init` with a cryptographic RNG: database role passwords, session pepper, TOTP encryption key, model server API keys, audit signing key, licence public key pinning.
- Stored in `/etc/synapse/secrets/` (root-owned, mode 0400), mounted into containers as Compose file secrets under `/run/secrets/`. Applications read `*_FILE` paths. Secrets never appear in environment variables, images, logs or git.
- **No default passwords anywhere.** A missing secret is a startup error.
- Vendor-side per-customer records (licences, configuration) are kept encrypted with sops and age.
- gitleaks runs in pre-commit and CI; a finding blocks the merge.

**Per-process credentials**

- Postgres roles: `synapse_api`, `synapse_worker`, `synapse_scheduler`, `synapse_migrator` (DDL only, not used at runtime), `synapse_audit_reader`, `synapse_backup`. Each has only the grants it needs.
- Each model server has its own API key, known only to the processes that call it.
- There is no key that grants user impersonation, because no process accepts user identity from another ([0002](0002-process-topology.md)).

**Network**

- Only Caddy publishes ports (80 and 443). Postgres and model servers are on an internal Docker network with no published ports.
- Worker containers that parse uploads have no outbound network access.
- TLS modes, chosen in the wizard: customer certificate from internal PKI (preferred), ACME DNS challenge, or Caddy's internal CA with its root certificate exported for the customer's IT to distribute.
- Headers: HSTS, strict CSP (`default-src 'self'`), `frame-ancestors 'none'`, `Referrer-Policy: same-origin`, `X-Content-Type-Options: nosniff`.
- Database connections inside the host network use TLS when the database runs on another machine (SaaS, or split on-prem installs).

**Containers**

- Non-root users, read-only root filesystems where possible, `cap_drop: [ALL]`, `no-new-privileges`, pinned image digests.

## Consequences

- Secrets cannot drift between environments because nobody types them.
- Rotating a secret is a `synapsectl` operation, which must exist and be tested.

## Alternatives considered

- **HashiCorp Vault on the box:** another stateful service with its own unsealing problem; file secrets cover a single host. Vault can back `synapsectl` for SaaS.
- **Environment variables:** visible in `docker inspect` and process listings.
